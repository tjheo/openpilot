# SVX 실시간 RPM (svx_live) — 읽기 전용, 선택 사항, 기본 꺼짐

콤마가 엔진 RPM(EMS11 0x316, 없으면 EMS_366 0x366)을 **읽기만** 해서, 같은 Wi-Fi(또는 테일넷)에 있는 폰의 SVX 가상배기음 앱(0.3.0 이상)에 보냅니다.
폰이 TCP로 콤마에 접속해 짧은 인사(핸드셰이크)를 하면, 같은 연결로 RPM이 계속 옵니다. **키, 명령어, 설정 파일이 없습니다.**

## 매일 쓰는 방법
1. 콤마 화면 **설정 → 토글**에서 이 기능을 켭니다. 한 번 켜 두면 계속 유지됩니다.
   * C4 화면(mici): **"svx live rpm to phone"** (C4 토글 화면의 다른 항목들처럼 영어 소문자로만 표시됩니다)
   * C3/C3X 큰 화면: **"SVX 실시간 RPM 폰 전송"** (한국어 설정일 때. 영어 설정이면 "SVX Live RPM to Phone")
2. 시동을 켭니다. 콤마가 주행 상태(onroad)가 되면 TCP 47816 포트에서 기다립니다.
   * 차가 움직일 필요는 없습니다. 정차 중이라도 시동이 켜져 있으면 됩니다.
3. 폰 앱에서 콤마 IP(처음 한 번 저장)를 확인하고 **[실시간 (콤마)]**를 누릅니다.

앱 화면에 지금 상태가 자동으로 표시됩니다: 연결 중 / 콤마 응답 없음 / 차량 인식 대기 / 지원하지 않는 차량 / EMS11 프레임 없음 / RPM 오래됨 / 거부됨 / 시간 초과 / 정상.
소리는 "정상"일 때만 납니다. 다른 상태가 되면 앱은 목표 음량을 바로 0으로 내립니다. 실제로 소리가 사라지기까지는 페이드아웃(최대 0.4초)과 오디오·전송 버퍼 지연이 더해집니다. 이 시간은 실차에서 측정하지 않았습니다.

## 동작 규칙
* **언제 실행되나:** 토글이 켜져 있고(`SvxLiveEnabled`), 장치가 onroad(`deviceState.started`)일 때만 manager가 `svx_lived`를 실행합니다.
  * 시동이 꺼진 상태(offroad)나 토글이 꺼진 상태에서는 실행되지 않습니다. 포트도 열리지 않고 CAN도 구독하지 않습니다.
  * manager는 꺼져 있을 때도 모듈을 미리 import합니다. 그래서 import만으로는 소켓, Params, 구독 같은 어떤 동작도 일어나지 않게 만들었습니다 (테스트로 확인).
* **끄기:** 토글을 끄면 약 0.5초 안에 폰 연결에 종료 신호(`BYE STOPPING`)를 보내고 프로그램이 끝납니다. manager도 1초 안에 정지시킵니다.
* **포트:** 파라미터 `SvxLivePort`(기본 47816, 1024~65535)입니다.
  * 평소에는 바꿀 필요가 없습니다. 화면에는 포트 편집 칸이 없습니다.
  * 다른 포트가 꼭 필요할 때만 이 파라미터를 직접 씁니다 (선택 사항).
  * 잘못된 값이면 포트를 열지 않습니다. 바꾼 뒤에는 토글을 껐다 켜야 적용됩니다.
* **누가 접속할 수 있나:** 사설 LAN(10/8, 172.16/12, 192.168/16)과 테일넷(100.64/10) 주소만 됩니다. 그 밖의 주소는 1바이트도 보내지 않고 바로 끊습니다.
  * **키가 없으므로 인증이 아닙니다.** 같은 네트워크의 누구나 RPM을 읽을 수 있습니다.
  * 폰이 보낼 수 있는 것은 인사(HELLO)와 연결 확인(PING)뿐입니다. 명령·설정·진단·쉘 기능은 없습니다. 폰이 보내는 어떤 내용으로도 차량, CAN, 파라미터, 파일을 바꿀 수 없습니다.
* **제한:** 동시에 폰 2대까지 받습니다. 같은 폰이 다시 접속하면 예전 연결을 대신합니다.
  * 접속 시도, 메시지 수, 버퍼 크기, 시간 초과에 모두 상한이 있습니다.
  * 50Hz 고정 주기로 동작하고 우선순위는 nice 19입니다.
  * 받는 쪽이 느리면 새 RPM을 쌓아 두지 않고 버립니다. 보내다 만 프레임 하나와 짧은 응답만 작은 상한 안에서 남습니다.
* **RPM 원본:** `can` 서비스를 **구독만** 하고 `CarParams` 파라미터를 **읽기만** 합니다.
  * 차량이 지원 차량으로 확인된 뒤에만 `can`을 구독합니다.
  * 다음은 전혀 하지 않습니다: 퍼블리셔 생성, sendcan, Panda/USB/socketcan 접근, 진단(OBD/UDS) 요청, 파라미터 쓰기.
  * 조향·제동·가속·모델 코드는 바꾸지 않았습니다.
  * 실제 RPM을 그대로 보냅니다. "4,000 rpm에서 최고 소리" 같은 대응은 앱 안에서만 합니다.

## 지원 범위 (이 밖은 소리 없음으로 거부)
* 차량 선택: `KIA_SELTOS`(hyundai), **CAN-FD 아님**. CAN **bus 0**의 EMS11(0x316)을 먼저 씁니다.
  * 레이아웃은 이 저장소 `hyundai_kia_generic.dbc`의 `EMS11` `N`입니다: 시작 비트 16, 16비트, 리틀엔디언, 0.25 rpm 단위 (테스트로 DBC와 대조).
  * EMS11이 한 번도 보이지 않으면 bus 0의 **EMS_366(0x366)** `N`을 씁니다: 시작 비트 8, 16비트, 리틀엔디언, 0.25 rpm 단위
    (같은 DBC, commaai/opendbc PR #319). 길이는 7 또는 8바이트만 받습니다. 고장 비트는 정의되어 있지 않습니다.
  * EMS11이 한 번이라도 보이면 그 연결(데이터 초기화 전까지)에서는 EMS11만 씁니다. 그래서 EMS11이 있는 차의 동작은 그대로입니다.
  * 근거: 실제 셀토스 녹화 2개(약 61초씩)에는 0x316이 어느 버스에도 없고, 0x366이 bus 0에 100Hz로 있습니다. 그 `N`은 TCU가 따로
    보내는 `TCU_DCT13`(0x162) `Cluster_Engine_RPM`과 프레임마다 거의 같습니다(정지 공회전 약 700rpm, 가속 시 상승).
    회전계나 OBD 같은 독립 기준값과 비교하지는 않았습니다. 시동 꺼짐(0) 상태는 녹화에 없었습니다.
* 다른 차, CAN-FD 셀토스, CarParams 없음은 각각 "지원하지 않는 차량" 또는 "차량 인식 대기"로 표시되고, 유효 RPM을 보내지 않습니다.
* CarParams는 2초마다 다시 읽습니다. 바뀌거나 사라지면 모든 데이터를 버리고 연결을 끊습니다 (`BYE CAR_CHANGED`). 폰은 새로 접속합니다.
  * CarParams는 onroad 전환과 manager 시작 때 지워지고 card가 새로 씁니다. 이 프로그램은 onroad일 때만 돌기 때문에 지난 주행의 값을 쓰지 않습니다.
* `carState.engineRpm`은 쓰지 않습니다. 현대/기아 carstate가 이 값을 채우지 않기 때문입니다.
* 둘 다 없으면 앱에 "EMS11 RPM 프레임 없음"이 표시됩니다(앱 문구는 바꾸지 않았습니다).

## RPM을 쓰지 않는 경우 (앱은 소리 없음)
* 다음 프레임은 쓰지 않습니다:
  * 300ms보다 오래된 프레임. 나이는 `logMonoTime` 기준이며, 큐에서 꺼낸 시각이 아닙니다. 밀린 큐를 늦게 읽어도 신선해지지 않습니다.
  * 미래 시각, 순서가 바뀐 프레임, 중복 프레임
  * 길이가 맞지 않는 프레임(EMS11은 8바이트, EMS_366은 7 또는 8바이트)
  * 다른 버스나 TX 에코에서 온 프레임
* 다음 경우에는 그보다 오래된 정상 데이터로 돌아가지 않고 즉시 "RPM 무효"를 보냅니다:
  * 가장 최근의 `can` 이벤트가 `valid=false`이거나 해석할 수 없을 때
  * 가장 최근 RPM 프레임이 거부되었을 때
* RPM 0은 엔진 정지로, F_N_ENG 고장 비트(EMS11만)·0xFFFF·9,000rpm 초과는 무효로 보냅니다.
* 앱 쪽 판정 (앱 0.3.0, 자세한 내용은 `PROTOCOL.md`):
  * 무효 상태가 오면 목표 음량이 바로 0이 됩니다 (그 뒤 페이드와 버퍼 지연).
  * 다시 소리를 내려면 새 프레임이 들어와야 합니다.
  * 앱이 보낸 연결 확인(PING)에 대한 최근 응답 뒤에 받은 데이터만 씁니다. 네트워크가 막혔다가 한꺼번에 들어온 옛 데이터는 신선하게 보이지 않습니다.

## 처음 설치·업데이트 (실제 배포와 구분)
이 저장소 작업에서 차량이나 콤마에 설치하거나 실행한 적은 **없습니다.** 아래는 안내입니다.
* 이 기능은 포크 브랜치에 들어간 코드입니다. 콤마가 이 코드를 실행하려면 이 기능이 들어간 버전으로 **업데이트한 뒤 재시작(재부팅)**해야 합니다.
  * `git pull`만 하고 재시작하지 않으면 이미 실행 중인 manager·UI가 계속 옛 코드로 돕니다. 토글도 보이지 않습니다.
* 새 파라미터(`SvxLiveEnabled`, `SvxLivePort`)는 `common/params_keys.h`에 있어서 params 모듈을 다시 빌드해야 인식됩니다.
  * 이 포크의 정상 업데이트·빌드 과정을 거치면 됩니다.
  * 빌드가 아직 반영되지 않았을 때는 토글이 화면에 나타나지 않고, manager도 이 프로그램을 실행하지 않습니다. 오류로 멈추지는 않도록 처리했습니다.
* 폰 앱도 **0.3.0 이상**이어야 합니다. 0.2.2 이하 앱(UDP)과는 호환되지 않습니다.

## 끄기 / 되돌리기
* 끄기: 토글을 끕니다. 기본값이 꺼짐이므로, 켜지 않은 장치에서는 아무것도 실행되지 않습니다.
* 되돌리기: 이 기능이 없는 이전 버전으로 되돌리면 됩니다. 남은 파라미터 값은 아무 효과가 없습니다.

## 예전 수동 송신기(tools/svx_rpm)
* 키를 만들고 SSH로 실행하던 수동 UDP 송신기(`tools/svx_rpm`, PR #1)는 이 기능으로 대체되어 제거되었습니다.
* 재사용한 부분: EMS11 해석, 차량 프로파일, 신선도 판정, `can` 구독 코드, 그리고 해당 테스트들입니다. 모두 이 폴더로 옮겼습니다.
* 0.2.2 이하 앱이 쓰던 SVX1 UDP 형식은 0.3.0 앱이 더 이상 받지 않습니다.

## 진단 로그 (NO_FRAME 원인 확인용, 자동)
토글이 켜져 있으면 `svx_lived`가 **자동으로** 짧은 진단 요약을 기존 cloudlog(swaglog)에 남깁니다. 따로 켤 스위치·명령·파라미터는 없습니다.
토글이 꺼져 있으면 프로그램 자체가 실행되지 않으므로 진단도, 구독도, 포트도 없습니다.

* **저장 위치 (코드로 확인):** `svx_lived` → `cloudlog.event("svxLiveDiag", ...)` → `/tmp/logmessage` IPC → `logmessaged`.
  * 장치 파일: `Paths.swaglog_root()` = **`/data/log/swaglog.<10자리 번호>`** (PC는 `~/.comma/log/`). INFO 이상만 기록합니다.
  * 파일은 60초마다 또는 256 KiB마다 새 번호로 바뀌고, 최대 2500개를 넘으면 **가장 오래된 파일부터 지워집니다.** 영구 보관이 아닙니다. 주행 후 너무 늦지 않게 가져오세요.
  * 같은 줄이 `logMessage`로도 발행되어 loggerd가 그 주행 구간의 `rlog`(`/data/media/0/realdata/<route>--<seg>/`)에 넣습니다. qlog에는 들어가지 않습니다. rlog도 저장 공간이 부족하면 deleter가 지웁니다. 업로드 동작은 바꾸지 않았습니다.
  * 파일 안에서는 swaglog가 키 뒤에 형식을 붙입니다: `kind$s`, `ticks$i`, `t$f`, `listening$b`, 목록은 `$a`.
* **무엇을 남기나:**
  * `start` (시작할 때 한 번): 프로파일, 주소 790(0x316), 예비 주소 870(0x366), 버스 `[0]`, 프로토콜 버전, 50Hz 주기, 300ms 신선도, 드레인 512 / 파싱 8, 검증된 `GitCommit`(40자리 hex가 아니면 `unknown`).
  * `summary` (시작 3초 뒤, 그다음 10초마다): 아래 카운터. `stop`: 종료 직전(서버·구독을 닫기 **전**) 마지막 요약.
  * `transition`: 표시 상태·차량 선택·구독 여부가 바뀔 때. 1초 간격, 10초 창마다 최대 4줄. 나머지는 개수만 셉니다.
  * 이벤트 내용(payload)은 4096바이트(UTF-8 JSON) 이하입니다. swaglog가 붙이는 줄 전체(장치 context 등 envelope)는 이 한도에 포함되지 않습니다. 1시간 주행이면 요약 약 360줄, 상태가 계속 바뀌는 최악의 경우 transition이 최대 1440줄 더해집니다.
* **남기지 않는 것:** CAN 데이터 바이트, RPM 값, 폰 IP 등 접속 주소, VIN·위치·토큰, 예외 메시지와 예외 이름(정해진 분류 `os`/`value`/`runtime`/… 만).
  * 같은 이유로 기존 텍스트 로그 `tick failed`, `can subscriber unavailable`도 분류만 남기도록 바꿨고, 후자는 최대 10초에 한 줄입니다(재시도는 그대로 2초).
  * 단, 기존 서버 로그(`session ... from <IP>`, 비허용 주소 거부)는 이번 변경 범위가 아니어서 그대로 접속 IP를 남깁니다.

### 다음 주행에서 쓰는 순서
1. 이 변경이 병합된 뒤, **주차 상태에서** 평소처럼 업데이트(git pull)하고 재시작(재부팅)합니다. 빌드도 평소 과정 그대로입니다.
2. 기존 토글 "svx live rpm to phone"은 켜 둔 그대로 둡니다. 새 설정은 없습니다. 폰 앱(0.3.0)도 바꿀 필요 없습니다.
3. 평소처럼 시동을 켜고 주행합니다. 원하면 앱에서 [실시간]을 눌러도 됩니다(진단은 앱 연결과 무관하게 남습니다). 주행 중에 조작할 것은 없습니다.
4. 주행 후 (주차 상태에서) 로그를 가져옵니다. 예: `grep -h svxLiveDiag /data/log/swaglog.* > /tmp/svx_diag.txt` 후 그 파일만 복사.
   * `svxLiveDiag` 줄만 골라도 각 줄의 swaglog envelope(`ctx`: 장치 ID, 브랜치 등, `host` 등)는 그대로 남습니다. **공개용으로 안전하지 않습니다.** 비공개로만 전달하거나, 공유 전에 `msg` 부분만 남기고 envelope를 지우세요.

### 해석 가이드 (`summary`의 `can` 안 값은 그 10초 창 기준)
아래는 **가설과 증거의 경계**입니다. 각 값은 이 프로세스가 본 것만 말하며, 원인을 단정하지 않습니다.
| 보이는 값 | 뜻 |
|---|---|
| `svxLiveDiag` 줄이 하나도 없음 | 이 코드가 실행됐는지 알 수 없음. 가능성: 업데이트·재시작 안 됨, 토글 꺼짐, onroad 아님, 로거/logmessaged 문제, 이미 회전·삭제됨 |
| `sel`이 `ok`가 아님 | 차량 선택 단계에서 멈춤 (`car_params_unavailable`/`unsupported_*`) |
| `subscriber_errors` > 0, `src: false` | `can` 구독 생성 실패 (`subscriber_error_types`에 분류) |
| `can.polls` > 0 인데 `drained` = 0 (`empty_polls` = `polls`) | 이 프로세스의 구독자가 `can` 메시지를 하나도 받지 못함. 차량·하네스·pandad·msgq 중 어디가 원인인지는 이것만으로 구분할 수 없음 |
| `read_errors` > 0 | 소켓 읽기 실패 (`source_errors`, 상태 INVALID) |
| `parse_errors` > 0 / `events_invalid` > 0 | 해석 불가 메시지 / pandad가 `valid=false`로 보낸 이벤트 |
| `events_valid` > 0, `rx_frames`에 버스별 프레임 있음, `rx_target` 비어 있음, `tx_target` 0 | 보관·파싱·집계된 표본(아래 한계 참고) 안에 0x316이 없었음. 차에 EMS11이 물리적으로 없다는 결론은 아님 |
| `rx_target`에 `"0"`이 아닌 버스만 있음 | 표본에서 주소 0x316 프레임이 다른 버스로 보였음(같은 주소라고 EMS11 내용이 확인된 것은 아님). **개수만 셀 뿐 받아들이지 않습니다.** 버스 변경은 별도 검증 후 따로 결정할 일입니다 |
| `tx_target`만 있음 | 송신 에코(src ≥ 128)에만 있음 |
| `rx_target."0"` > 0, `matches` > 0, `accepted` = 0 | 프레임은 맞지만 거부됨: `state_rejects`(`too_old`/`future`/`out_of_order`/`len`), `event_age_ms` 확인 |
| `accepted` > 0, `sample_reasons` | 정상 수신. `ok`/`engine_stopped`/`sna`/`fault`/`implausible` 분포 |
| `drain_saturated` > 0, `drain_discarded`·`late_ticks`·`tick_gap_ms.max` 큼 | 큐가 밀렸고 틱이 늦었음. 스케줄링(nice 19) 지연이 한 가설 |
| `status_ticks` | 그 창에서 앱에 보낸 상태별 틱 수 (`no_frame`, `ok`, `stale`, …) |
| `sessions`, `server` | 앱 연결 수와 서버 카운터 변화 (주소는 없음) |

### 진단의 한계
* 프레임 집계는 **실제로 파싱한 메시지만** 셉니다: 틱마다 꺼낸 최대 512개 중 최신 8개(원래 RPM 경로가 파싱하는 것). 나머지는 내용을 모르는 채 버려지고 `drain_discarded`로만 셉니다. 정상(100Hz `can`, 50Hz 틱)이면 틱당 1~2개라 전부 파싱됩니다. 한 틱에 최대 2048 프레임까지만 세고 넘으면 `census_skipped_frames`.
* 프레임 집계(`rx_target` 등)는 지금도 0x316만 셉니다. 0x366으로 RPM을 받을 때도 `rx_target`은 비어 있을 수 있습니다(`accepted`는 늘어납니다).
* `rx_target`이 비어 있어도 "차에 EMS11이 없다"를 증명하지 못합니다. 이 프로세스가 보관·파싱·집계한 표본에 없었다는 뜻일 뿐입니다(하네스 위치, 판다 필터, 상위 처리, 표본 밖 메시지 모두 가능).
* `can` 메시지가 0개여도 차량·하네스 문제인지 장치 소프트웨어 문제인지 구분하지 못합니다. 이 구독자가 받지 못했다는 사실만 남습니다.
* 진단 줄이 없는 것도 증거가 아닙니다(로거 실패, 회전·삭제, 미실행 모두 가능). `emit_errors`는 기록된 다음 줄에만 나타납니다.
* 시간 값 `t`는 이 프로세스 시작 기준 monotonic 초입니다. 장치 시계가 주행 중 바뀌어도 영향이 없지만, swaglog `created`(벽시계)는 바뀔 수 있습니다.
* 집계 비용: 개발 서버(x86)에서 합성 이벤트(이벤트당 151프레임, 틱당 2개)로 틱당 약 0.43ms 추가(20ms 주기 대비). **장치(ARM)에서는 측정하지 않았습니다.**
* 로그는 회전·삭제되므로 오래 보관되지 않습니다.

## 한계
* 실제 콤마·차량·폰에서 실행해 보지 않았습니다 (`VERIFICATION.md`). EMS11/EMS_366의 실시간 동작과 지연은 실차 확인이 필요합니다(EMS_366은 녹화 재생으로만 확인).
* 이 서버에는 msgq·raylib가 빌드되어 있지 않습니다. 그래서 다음은 실행하지 못했습니다:
  * 실제 `can` 소켓 구독
  * 실제 화면 그리기
* 대신 다음 방식으로 확인했습니다:
  * 실제 cereal 스키마로 만든 이벤트를 넣는 테스트
  * 위젯을 대체한 설정 화면 테스트
  * 실제 TCP 소켓으로 Python 서버와 앱(JVM) 클라이언트를 연결한 테스트
* `params_keys.h`는 g++로 따로 컴파일해 두 키만 확인했습니다. 전체 scons 빌드는 하지 않았습니다.
